## Days 51–60: what's new in this zip

### Days 51–54 — Experiments + analysis
Three scripts, each targeting one architectural claim:
- `experiments/exp1_memory_speedup.py` — same task, first time vs. immediate repeat. Does memory make the repeat faster / need fewer attempts?
- `experiments/exp2_mcp_overhead.py` — real MCP protocol round-trips vs. an equivalent direct filesystem call. What does dynamic tool discovery actually cost?
- `experiments/exp3_repeat_bug_trend.py` — five *different* tasks sharing one bug pattern, run in sequence. Does the attempts-needed trend downward as memory accumulates related fixes?
- `experiments/analyze_results.py` — turns all three into charts (`experiments/results/*.png`) and a `summary.md` table.

**Run these for real** against your live stack once your model is pulled:
```bash
docker compose up -d --build
python3 experiments/exp1_memory_speedup.py
python3 experiments/exp3_repeat_bug_trend.py
cd backend && python3 ../experiments/exp2_mcp_overhead.py && cd ..
python3 experiments/analyze_results.py
```

**Important — read this before you trust any numbers in the paper draft:**
`experiments/results/` already contains real output — but it was generated by
running the *actual* FastAPI app, LangGraph orchestration, Postgres/pgvector,
and Redis, with only the outermost Ollama and MCP network calls **simulated**
(scripted latency + scripted pass/fail outcomes), since this was built in a
sandbox with no GPU. This proves the harness itself works end-to-end and
produces the right *shape* of result — it is **not** a claim about real model
quality. Re-run the four commands above against your real model before you
present or submit any numbers. The scripts don't need to change; only the
data will.

## Phase 9: fixed the event-loop-blocking bug from a real run

You ran the full stack for real and hit "Lost the live connection to the
backend" — this phase is the actual fix, diagnosed from your logs, not
guessed at.

**Root cause.** `app.llm.generate()` calls Ollama via the synchronous
`requests` library, and every LLM call site (`planner.plan()`,
`developer.generate_code()`, `scaffolder.scaffold_webapp()`, plus
`app.memory`'s embedding calls) was invoked as a plain, unwrapped call
inside `async def` node/handler functions. A synchronous call inside an
`async def` doesn't yield — it freezes the entire event loop, and with it
every open WebSocket, for however long that one call takes. Your logs
confirm this exactly: single `generate()` calls routinely took 15–100+
seconds with zero other backend activity logged in that window, and once
the loop was frozen long enough, the browser gave up on the WebSocket and
you saw the disconnect banner — while the pipeline kept running
server-side, because the background task itself was never dead, just
unable to talk to anyone.

**Fix.** Every blocking call site (`app/pipeline/nodes.py`,
`code_handler.py`, `webapp_handler.py`) now runs via
`await asyncio.to_thread(...)`, which moves the blocking work onto a
separate thread and lets the event loop keep servicing WebSocket frames
(and other concurrent requests) while it waits. Verified for real, not
assumed: `scripts/test_event_loop_not_blocked.py` runs an actual 0.6s
blocking call through the exact same code path as production, alongside a
concurrent "heartbeat" coroutine, and asserts the heartbeat kept ticking
throughout instead of stalling until the blocking call finished — this is
the same class of check that would have caught the original bug before it
shipped.

**Also fixed: the Langfuse 401 log spam.** Your logs show
`Failed to export span batch code: 401, reason: Unauthorized` after
nearly every single call — `app/llm.py`'s `@observe` decorator was never
actually a no-op without a configured key (the docstring's old claim was
wrong); it kept trying to export traces to Langfuse's cloud host regardless.
Fixed by setting Langfuse's own documented `LANGFUSE_TRACING_ENABLED=false`
env var whenever `LANGFUSE_PUBLIC_KEY` isn't set, so tracing is genuinely
disabled instead of failing loudly on every call — this was also drowning
out the real errors in your logs, making the actual bug harder to spot.

**Not a bug — confirmed working as intended:** the pgvector fix you
diagnosed yourself (switching to `pgvector/pgvector:pg16`) is correct and
already reflected in your `docker-compose.yml`; your own logs show memory
retrieval succeeding with real candidates once that image was in place.
No changes needed there.

**One thing flagged, not fixed — needs your input:** in your second run,
`ifs=0.0` appears for every single task, with no variation at all, which
is a very different pattern from the mixed 0.33/0.66/1.0 scores in your
first run. This isn't necessarily a bug — the metric returns `0.0` when
the extractor genuinely finds request entities that never appear in the
generated code (e.g. if your request named a specific filename and the
model invented a different one every attempt) — but the total uniformity
across 7 different tasks is unusual enough to be worth a second look with
the actual request text, which isn't visible in the logs. Flagging rather
than guessing at a fix.

## Phase 8 (new): production-level reorganization

No new behavior in this phase — a pure structural refactor, verified by
re-running every existing test script unchanged and confirming identical
results, plus new tests proving the specific extensibility claims below.
The goal: each component (a task type, an MCP tool, a UI piece) should be
addable/modifiable independently, without touching unrelated files.

**Backend — `app/pipeline/` package** (was a single, growing `graph.py`
that had accumulated if/else branches on `task.type` in two different
places — `developer_node` and `qa_node` — that had to be kept in sync by
hand):
- `pipeline/event_types.py` — every event type name the pipeline can ever
  emit, in one place, as constants (`ev.QA_RESULT`, not the string
  `"qa_result"` typed inline). A typo here is now an `AttributeError` at
  import time instead of a silent frontend mismatch.
- `pipeline/task_handlers/` — the actual extension point. `base.py` defines
  the `TaskHandler` contract (an ABC — Python actually refuses to
  instantiate an incomplete one, not just a type-checker warning);
  `code_handler.py` and `webapp_handler.py` are the two existing task
  types, moved verbatim (no logic changes); `__init__.py` is a one-dict
  registry. **Adding a new task type is one new file + one line in that
  registry — `nodes.py` and `graph.py` need zero changes.** This isn't just
  asserted: `scripts/test_pipeline_reorg.py` registers a real dummy handler
  at runtime and proves the existing dispatch code picks it up unmodified.
- `pipeline/nodes.py` — the actual LangGraph node functions, now holding
  only what's genuinely shared across task types (state bookkeeping, event
  narration, long-term memory retrieval, retry/escalate decisions);
  task-type-specific generation logic lives in the handlers above.
- `pipeline/graph.py` — thin: just `StateGraph` wiring and `run_pipeline()`.
- `app/graph.py` (the old monolith) is gone, not kept as a compatibility
  shim — `main.py`'s one import line was updated instead.

**MCP server — `mcp_server/tools/` package** (was one `server.py` with
every tool's implementation inline, including `check_webapp`'s ~100-line
runtime probe):
- `workspace.py` — the shared per-project path-safety logic (`project_dir`,
  `safe_join`), used by every tool, previously embedded in `server.py`.
- `tools/write_file.py`, `run_shell_command.py`, `run_tests.py`,
  `check_webapp.py` — one file per tool. `tools/__init__.py` is the
  registry (`ALL_TOOLS`); `server.py` just loops over it and calls
  `mcp.tool()(fn)` — it no longer imports or knows about any individual
  tool. **Adding a new tool is one new file + one line in `ALL_TOOLS`.**
  Verified against the real pinned `mcp==1.9.4` package (not a stub): all
  4 tools register correctly on a real `FastMCP` instance.

**Frontend — `App.jsx` split** (was one file holding WebSocket handling,
event-to-display logic, and every component):
- `constants/eventTypes.js`, `constants/agents.js` — display-mapping data,
  hand-mirrored from the backend's `event_types.py` (documented as such,
  since JS can't import a Python module).
- `lib/describeEvent.js` — pure functions (event → bubble text/badge/code),
  no React, no state.
- `hooks/usePipelineSocket.js` — all WebSocket/state logic, independent of
  any rendering.
- `components/Bubble.jsx`, `CodeBlock.jsx`, `ChatComposer.jsx` — pure
  presentational pieces.
- `App.jsx` is now ~45 lines of composition — no business logic left in it.
- Verified: `npm run build` succeeds (39 modules now vs. 32 before —
  everything is actually wired in, not orphaned), output bundle size
  essentially unchanged, confirming this changed organization, not behavior.

**What was deliberately left alone:** `config.py`, `db.py`,
`redis_client.py`, `memory.py`, `short_term_memory.py`, `llm.py`,
`mcp_client.py`, `schemas.py`, `ifs.py`, `webapp_detect.py` — each is
already a single-responsibility module at the flat `app/` level. Nesting
them into `core/`/`domain/` subfolders would have touched many import
lines across the codebase for organization's sake alone, with no
corresponding reduction in coupling — the actual monoliths were the
pipeline dispatch logic and the MCP tool file, both addressed above.

## Phase 7 (new): website/web-app scaffolding + real code visible live

Two things, addressing the two biggest remaining gaps: the pipeline could
only produce single files, and the live UI narrated what agents did without
ever showing what they actually wrote.

**Web-app scaffolding**
- `app/webapp_detect.py` — lightweight keyword heuristic on the incoming
  request ("website", "web app", "landing page", "flask app", etc.).
- `app/agents/planner.py` — when a request reads as a website build, skips
  the normal per-function task decomposition entirely (no LLM call spent
  deciding how to chop up a request that isn't naturally a sequence of
  independent functions) and returns a single `Task(type="webapp_scaffold")`.
- `app/agents/scaffolder.py` (new) — generates a complete, minimal FastAPI +
  Jinja2 app (`main.py`, `requirements.txt`, `templates/*.html`,
  `static/style.css`, more files/pages if the request implies them) as a
  JSON file manifest. Falls back to a guaranteed-runnable minimal site if
  the model's output can't be parsed — same philosophy as the Planner's own
  existing fallback, never a hard crash.
- `mcp_server/server.py` — new `check_webapp` tool: py_compiles every `.py`
  file in the scaffolded project and confirms `requirements.txt` exists,
  returning the *exact same* `PASSED/EXIT_CODE/OUTPUT` text format as
  `run_tests`, so QA's existing parser needed zero changes.
- `graph.py` — `developer_node` now dispatches to `_run_webapp_scaffold`
  (writes every file via MCP `write_file`, then best-effort sets up an
  isolated `.venv` and installs `requirements.txt` via `run_shell_command`)
  instead of `_run_code_task` when `task.type == "webapp_scaffold"`; `qa_node`
  calls `check_webapp` instead of `run_tests` for the same task type.
- Try it: `"build a website for a bakery with a homepage and a contact page"`.

**Real code, visible live**
- `developer_done` and the new per-file `developer_file_written` events now
  carry the actual generated code (capped at 6000 chars per event), not
  just a filename and byte count.
- The frontend chat feed renders it in a real code block under each agent
  bubble. For a scaffolded web app you see every file appear as its own
  bubble, in order, with its actual content — not one final "done" message.
- Honest scope note: this is NOT token-level streaming — each file/task's
  code arrives as one event once that generation call completes, not
  character-by-character as the model writes it. True token streaming would
  mean switching `llm.generate()` to Ollama's streaming API and emitting
  incremental chunks; that's a bigger, separate change, not done here.

**Follow-up fix (same session):** the initial Phase 7 cut had two real gaps —
webapp retries regenerated blind with no memory of what broke, and the
communication-mode ablation (Phase 6) didn't apply to webapp tasks at all
(since `task.description` was just the raw request verbatim — there was
nothing for "message_passing" mode to lose). Both fixed: `scaffold_webapp`
now takes `previous_failure` (same as `developer.generate_code`), and the
Planner now genuinely summarizes a website request into a task description
distinct from the raw request, so `blackboard` mode giving the Scaffolder
the original request back is a real difference again. Covered by
`scripts/test_scaffolder.py`'s retry/mode tests and the updated
`scripts/test_planner_routing.py`.

**Follow-up fix #2 (same session): `check_webapp` now actually boots the app.**
Previously it only `py_compile`d files — a genuine gap, since a file can
compile cleanly and still crash on every real request. `check_webapp` now
runs in two stages: py_compile (required to pass) then, if that succeeds
and the project's own `.venv` is ready, a real boot-and-probe — starts the
app with uvicorn against the project's own venv (not the MCP server's),
makes an actual HTTP GET to it, and reports pass/fail on that too. Skips
the runtime stage gracefully (doesn't fail the check) if `.venv` isn't
ready yet, since that's a separate, already-reported concern. Verified for
real, not mocked: `scripts/test_check_webapp.py` builds an actual venv,
installs real fastapi/uvicorn into it, and confirms (a) a genuinely working
app boots and responds, and (b) a route that compiles fine but throws on
every request (a bug py_compile alone would miss) is correctly caught and
fails the check. Writing this test surfaced a real bug in the first cut —
a request timeout during the crash case raised `TimeoutError`, which
wasn't in the original exception handler — fixed on the spot.

## Phase 6 (new): communication-mode ablation

Directly addresses the base-paper gap against SE-Blackboard (Liu et al.,
IEEE Access 2026): their whole contribution is comparing communication
architectures under an identical pipeline, and until now AIOpsForge only
had one mode.

- `AgentState.communication_mode` (`schemas.py`) — `"blackboard"` (default)
  or `"message_passing"`, settable per-request via
  `POST /request` or `/request/async` with
  `{"request": "...", "communication_mode": "message_passing"}`.
- `developer.generate_code(..., original_request=...)` — the actual
  mechanism. In `"message_passing"` mode the Developer sees ONLY the
  Planner's task description (this was AIOpsForge's original, implicit
  behavior). In `"blackboard"` mode it ALSO receives the raw original user
  request, so it can recover detail the Planner's one-line summary may
  have compressed away. This mirrors SE-Blackboard's own formal context
  functions, C^MP(Coder) = {out(Planner)} vs. C^BB(Coder) = {A, I} — see
  the docstring in `app/agents/developer.py` for the full mapping.
- The active mode is announced in the live event stream
  (`pipeline_start`), so it's visible in the chat UI during a demo, and
  logged per-run in the `runs` table (`communication_mode` in the
  developer stage's output JSON) for later analysis.
- `scripts/test_communication_modes.py` — proves the two modes produce
  genuinely different prompts for an identical task (not a no-op flag),
  with no live Ollama required.

This is the foundation for the IFS-equivalent metric and the real
experiment reruns comparing the two modes — both still pending.

## Phase 5: live agent-communication demo layer

What changed, on top of everything above:

- `backend/app/events.py` — a small async event bus. Every graph node
  (Planner/Developer/QA/next_task/escalate) now publishes a human-readable
  event as it works, instead of only writing to Postgres for later polling.
- `WS /ws/projects/{project_id}` in `backend/app/main.py` — streams those
  events live. A client that connects a moment late (or reconnects) still
  gets the full history replayed first, so nothing's missed mid-demo.
- `frontend/src/App.jsx` (rewritten) + `frontend/src/FlowDiagram.jsx` (new)
  — the dashboard is now a chat interface: your request is a chat message,
  and every agent action (planning, writing code, running tests, retrying,
  escalating) appears as a labeled bubble from that agent in real time. A
  live SVG diagram above the chat highlights whichever node — Planner,
  Developer, or QA — is currently active, and lights up the retry/escalate
  edges when they fire. This is what you'd actually run during a live demo
  or a viva instead of narrating a polling task list.
- The old `GET /projects/{id}/status` polling endpoint is untouched and
  still works, in case you want it for a non-live/scripted check.
- `scripts/test_events.py` — standalone check of the event bus (live
  delivery order, late-join replay, cross-project isolation), no
  Postgres/Redis/Ollama required to run it.

No new services in `docker-compose.yml` — this lives entirely inside the
existing `backend` and `frontend` containers, so `docker compose up -d --build`
picks it up as-is.
